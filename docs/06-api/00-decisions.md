## Decisions made in this document set

| ID | Decision | Why | Status |
|---|---|---|---|
| D-130 | **Contract first.** [`openapi.yaml`](openapi.yaml) is the source of truth for paths, bodies, roles, and errors, and the backend must implement it. There is one API, for the web application; there is no public partner API in the MVP. | The sample API folder does the same. A second API would need its own security and support, and no story asks for one. | Call, awaiting user review |
| D-131 | **Session.** Login sets an opaque session id in an HttpOnly, Secure, SameSite=Strict cookie (`mp_session`). The session is kept on the server, so that a deactivated user's next request is refused (AC-02.5). Every state-changing request also sends the header `X-CSRF-Token`, whose value login and getSession return. The security schemes are `sessionCookie` (apiKey in a cookie) and `csrfHeader`. Where the session is stored is an architecture decision. | AC-02.5 asks that open sessions end on the next request, which a signed token cannot do without a server list. A cookie session needs a CSRF defence. | Call, awaiting user review |
| D-132 | **Entity scope comes from the session** (D-13, BR-09), never from a path or a body. No path carries an entity code. An identifier that the caller's scope cannot see returns **403 ACCESS_DENIED with no data, whether or not the record exists in another entity**, so identifiers cannot be probed across entities (AC-01.5). The Group Admin and the Demo Operator belong to the group: the Group Admin gets per-entity aggregates only where SCR-75, SCR-60, and SCR-61 allow, and the Demo Operator passes `entityId` only on the simulator operations (SCR-80 picks the entity). | The routes page and the data model already say that a foreign record is answered like a missing one. A 404 for a missing record and a 403 for a foreign one would tell the caller which exists. | Call, awaiting user review |
| D-133 | **Roles.** `x-roles` on every operation lists values of the DBML enum `user_role` only. Finer rules (own entity, own level, own delegation, BR-02 separation of duties, BR-36 self-signing block) are written in the description and listed in `x-rules`. The server enforces everything; a hidden control is UX only. | One enum is the single list of roles in the database, the permissions table, and the API. | Call, awaiting user review |
| D-134 | **Traceability extensions on every operation:** `x-stories` (active US ids, at least one), `x-rules` (BR ids, may be empty), `x-screens` (SCR ids where the result is used; empty only for a system operation), `x-tables` (DBML table names the operation reads or writes, at least one), and optionally `x-criteria` (the acceptance criteria it serves). | The API must show that every story has an API and every API uses a table. Extensions in the contract keep the proof next to the operation, and the checker reads them. | Call, awaiting user review |
| D-135 | **Background work is not HTTP.** The AI checks (UC-12..UC-16), the scheduled ERP sync, the mailbox fetch, the status lookups, the reminders, and the ERP send run as server jobs. Their results are read through operations. An operation that starts a job returns **202 Accepted** with the run id (see D-145 for which). The jobs are listed in [API traceability](01-api-traceability.md#4-background-jobs) with the tables they write. | A check run, a sync, and a send take longer than a request should wait, and the model call must not hold a transaction (DF-08). | Call, awaiting user review |
| D-136 | **Optimistic concurrency.** A record with a `version` column takes `version` in the body of an update or action. A stale version returns 409 `VERSION_CONFLICT` with the current record (D-30, BR-37, and the conflict states of the information architecture and UI/UX documents). | The data model checks versions in the same transaction; the API must carry the version the user saw. | Call, awaiting user review |
| D-137 | **Idempotency.** Signing (one or many requests), batch release, and ERP send or resend accept an `Idempotency-Key` header; a repeat with the same key returns the first result. Signing many requests in one action returns a per-request result list (each signed or refused with its reason), never a partial silent success. | A double click or a retry after a lost answer must not sign or send twice (AC-26.12). | Call, awaiting user review |
| D-138 | **Money and time.** Money is a decimal string in VND (`"70050000.00"`, with a pattern), never a JSON number; rates, tolerances, quantities, and probabilities are decimal strings too. Dates are `YYYY-MM-DD`; date-times are ISO 8601 with an offset; the server time zone for periods is Asia/Ho_Chi_Minh. | A JSON number loses exactness; the database uses `numeric` (DF-53). | Call, awaiting user review |
| D-139 | **Errors** are RFC 7807 Problem Details (`application/problem+json`) with `errorCode`, `detail`, `traceId`, and `errors` for validation. Codes: AUTH_INVALID_CREDENTIALS, AUTH_SESSION_EXPIRED, ACCESS_DENIED, VALIDATION_FAILED, RESOURCE_NOT_FOUND, VERSION_CONFLICT, STATE_CONFLICT (a lifecycle transition that is not allowed from the current state; `detail` cites the BR-33, BR-34, or BR-35 transition), SEPARATION_OF_DUTIES (BR-02, BR-36), RULE_LIMIT_EXCEEDED (BR-16), FILE_REJECTED (with `rejectionReason`), DEPENDENCY_UNAVAILABLE, RATE_LIMITED, INTERNAL_ERROR. Per D-132, an unknown id of a scoped record gives ACCESS_DENIED; RESOURCE_NOT_FOUND is for lookups with no scope (only the demo routes when the demo flag is off). | The sample API uses the same shape. A stable code lets the interface react without reading text. RFC 7807 itself was not opened: its field names are Unverified (a reading of RFC 7807, replaced by RFC 9457, would confirm them). | Call, awaiting user review |
| D-140 | **Lists** take `page` (1-based) and `pageSize` (default 25, at most 100) and return `{items, meta:{page, pageSize, totalItems, totalPages}}`. Search and filters are query parameters that match the SCR-10 query string. The saved-view tabs of the interface are filter presets in the client, not API objects. | The routes page keeps filters in the query string so that Back restores them. | Call, awaiting user review |
| D-141 | **Files.** The XML upload is multipart (one or many files; limits in DF-85). The original XML is downloadable unchanged with its hash, and so is the cancellation notice file (DF-81). | AC-10.1 stores the file unchanged with a hash as evidence. | Call, awaiting user review |
| D-142 | **Derived values have no table.** Rates, badges, counts, retry counts, alerts, dashboard and group overview figures, the state of a delegation, and the accuracy of a gate are computed by read operations. Each description says so and names the tables it computes from. | D-63 stores no derived value. | Call, awaiting user review |
| D-143 | **The ERP simulator API** lives under `/demo/erp-simulator/...`, tag `Demo`, role DEMO_OPERATOR only. It uses only `sim_*` tables and `entities`, and is disabled outside a demo deployment (404 when the demo flag is off). The link from MatchPay to an ERP is not an HTTP API in this contract: it is a server-side port, decided in the architecture. | The simulator is not part of the product (AC-08.7), and the sync copies the simulator into the `erp_*` tables like any ERP (D-49). | Call, awaiting user review |
| D-144 | **Audit.** No operation writes `audit_log` directly. Every state-changing operation appends to it in the same transaction, so its `x-tables` lists `audit_log`. The audit list is read-only and filterable; it has no edit or delete operation. | BR-12, D-55, and DF-30 make the entry part of the action. | Call, awaiting user review |
| D-145 | **Which operations return 202.** An operation returns 202 with the run id when the main work continues after the response: `uploadInvoices`, `startErpSync`, `startMailboxFetch`, `rerunChecks`, `runAuthorityLookup`, every exception resolution that runs UC-16 again (`confirmLineMatch`, `correctFlow`, `confirmEntity`, `confirmAiResults`), `decideTaxRiskHold`, `decideServiceAcceptance`, and `resendToErp`. `releaseBatch` and `signPaymentRequests` return 200, because the requests and the signatures are saved inside the call; the AI summaries and the ERP send that follow are jobs that the next read shows. This sharpens D-135, which names "release/send". | A client that waits for a 200 on a release would otherwise wait for the AI summaries (AC-25.13). | Call, awaiting user review |
| D-146 | **Error codes beyond D-139, and their HTTP status.** AUTH_ACCOUNT_DEACTIVATED (403) separates a deactivated account from a wrong password, because AC-01.3 shows a different text. Uniqueness failures (email, tax code, a second active profile, an overlapping delegation) are 422 VALIDATION_FAILED on a field. The statuses are 401 for AUTH_INVALID_CREDENTIALS and AUTH_SESSION_EXPIRED; 403 for ACCESS_DENIED and SEPARATION_OF_DUTIES; 404 RESOURCE_NOT_FOUND; 409 for VERSION_CONFLICT and STATE_CONFLICT; 422 for VALIDATION_FAILED, RULE_LIMIT_EXCEEDED, and FILE_REJECTED; 429; 500; and 503. | AC-01.2 and AC-01.3 name two different messages. | Call, awaiting user review |
| D-147 | **The Group Admin names an entity on user operations.** `listUsers`, `createUser`, and `listErpUsers` take `entityId` (query or body) for the Group Admin only, because SCR-70 and SCR-71 let the Group Admin choose the entity. For an Entity Admin the field is ignored and the own entity is used. This is the one place besides the simulator where a caller names an entity; it narrows D-132 for a role that belongs to the group. | AC-02.1 and SCR-70 need a Group Admin to create a user in a chosen entity. | Call, awaiting user review |
| D-148 | **Exception resolutions are separate operations**, one for each action of AC-18.1: take, confirm a line match, correct the flow, confirm the entity, report a wrong entity, record the gate comparison, reject, send for a decision, draft a correction or data-fix notice, record a cancellation notice, and confirm a follow-up. Each carries the `version` of the exception (or of the invoice). | The actions have different bodies, roles, and refusals; one generic "resolve" body would hide them. | Call, awaiting user review |
| D-149 | **Re-runs.** Only the AP Accountant can start a new check run (`rerunChecks`, DF-08, AC-12.5) or repeat the authority lookup (`runAuthorityLookup`, AC-10.15). Nothing else is re-run by hand; an AI summary or a sample is never re-run on request. | These are the only two re-runs that a story allows. | Call, awaiting user review |
| D-150 | **A delegate signs through the same operation.** `signPaymentRequests` has no delegation field. The server finds the active, unrevoked delegation of the caller and the role the request waits for, signs at the delegator's level, and records both people (BR-38, AC-30.2). The queue marks such requests `onBehalfOfName`. | A client cannot claim a delegation. The record must follow the server's own check. | Call, awaiting user review |
| D-151 | **Withdrawal is a sub-resource of the invoice** (`POST /invoices/{invoiceId}/batch-withdrawal`) and carries the invoice `version`. It is tagged Batch. | SCR-12 and SCR-30 both start it (AC-24.7, AC-17.12), and the invoice is the object that changes state (V15). | Call, awaiting user review |
| D-152 | **Closing a gate clears its open alert** (`gate_alerts.cleared_by` and `cleared_at`). No source says when an alert is cleared. | AC-06.7 says the alert recommends closing and the gate stays open until the Group Admin acts; closing is that act. | Call, awaiting user review |
| D-153 | **A wrong password when signing** gives 401 `AUTH_INVALID_CREDENTIALS` for the whole action; no request is signed and a `LOGIN_FAILED` audit entry is written. The modal stays open (SCR-52). | The password check comes before any request is looked at, so there is no per-request result to give. | Call, awaiting user review |
| D-154 | **A manual ERP sync operation exists** (`startErpSync`, AP Accountant) although no screen has a "Sync now" control. It has no `x-screens`. It serves the demo, where an operator creates an order and should not wait 15 minutes, and the tests. | D-135 names a manual sync; the screens do not show one. See the gaps. | Call, awaiting user review |
| D-155 | **Dashboard figure lists.** `listDashboardFigureInvoices` is open to the AP Accountant, the Chief Accountant, and the Payment Approver, who may open the worklist. The Entity Admin sees the counts of SCR-60 and no list, because AC-17.9 denies an administrator the worklist. | SCR-60 says "every figure opens a list", while AC-17.9 says an Administrator gets "Access denied" on the worklist. | Call, awaiting user review |
| D-156 | **BR-09 and BR-12 in `x-rules`.** Both rules apply to every operation (D-132, D-144). They are listed in `x-rules` only on operations whose acceptance criteria cite them, so that a rule list shows what is specific to an operation. The Related API lines of the business rules follow `x-rules`. | Listing them on every operation would put 100 or more ids on two rules and hide the rest. | Call, awaiting user review |
| D-157 | **Downloads.** `downloadInvoiceDocument` returns `application/xml` and `downloadCancellationNotice` returns `application/octet-stream`; both send `X-Content-SHA256` with the hash that the database stores and `Content-Disposition: attachment`. | AC-10.1 and DF-81 keep the hash as evidence; a client can compare it. | Call, awaiting user review |
| D-158 | **A failed correction-request email is data, not an error.** `sendCorrectionRequest` returns 200 with `sendStatus` NOT_SENT and `lastError` when the Email Service fails; the exception does not change state, and the same call retries (AC-19.6). | The row is saved as NOT_SENT, and the interface needs the saved draft in the answer. | Call, awaiting user review |
| D-159 | **Upload result.** `uploadInvoices` returns 202 with one result per file: ACCEPTED, REJECTED_INVOICE (an XML stored as a Rejected invoice), or REJECTED_FILE (not XML or too large; no invoice is created). FILE_REJECTED (422) is for a request that is unusable as a whole: no file part, or more files than the limit. The result of a rejected non-XML file is not stored (data model, SCR-11), so there is no operation that reads an old upload result; the audit entry is the record. | AC-10.8 and AC-10.10 need a failing file not to stop the others. | Call, awaiting user review |
| D-160 | **Short lists are not paginated.** Sectors, delegation candidates, message templates, the lines of an invoice, the follow-ups of an exception, the correction requests of an exception, the cancellation notices of an invoice, the check runs of an invoice, the lookups of an invoice, the requests of a batch, and the send attempts of a request return `{items}` without `meta`. | Each is bounded by the object it belongs to. | Call, awaiting user review |
| D-161 | **Evidence has one aggregated read and one per-run read.** `getInvoiceEvidence` returns what SCR-12 shows from the latest run; `getCheckRun` returns the full outputs of any run, so earlier decisions stay readable (AC-16.13). AI-written text carries `aiGenerated` so the interface can label it (AC-17.3). | SCR-12 loads once; the audit view of an old run is rarer. | Call, awaiting user review |
| D-162 | **Computed states are API enums with no DBML twin.** DelegationState (Scheduled, Active, Ended, Revoked), SendPhase, AgeBucket, AcceptanceSource, DecisionKind, and similar values are derived (D-142) and are not stored. They are not marked `x-dbml-enum`. | The database has no column for them (D-63). | Call, awaiting user review |
| D-163 | **Search text.** `q` on `listInvoices` matches part of an invoice number or part of a supplier name; when it reads as a number it also matches the exact total with VAT, ignoring thousands separators (DF-68). A text such as `0000123` can match a number and a total, and both are returned. | DF-68 describes one search box with three kinds of match. | Call, awaiting user review |
| D-164 | **Refusals are audited by the server's shared handling,** not by an operation: every 403 on a protected function writes an ACCESS_DENIED entry, and a failed login writes LOGIN_FAILED (AC-01.2, AC-01.8). This does not conflict with D-144, because no operation body writes the entry. | AC-01.8 asks that a bypass attempt is logged. | Call, awaiting user review |

## Defaults pending confirmation

Numbers that no earlier document fixes. Each one is a default chosen so that the contract is complete; change any of them without changing the structure of the contract.

| ID | Default | Status |
|---|---|---|
| DF-83 | **Page size.** `pageSize` defaults to 25 and is at most 100 (D-140). The invoice worklist client sends 50 (DF-68). | Default, pending confirmation |
| DF-84 | **Session lifetime.** A session ends after 30 minutes without a request, or 12 hours after login. Login issues a new session id and a new CSRF token. | Default, pending confirmation |
| DF-85 | **Upload limits.** At most 20 files per upload request, 10 MB for each file (the limit of DF-79 and DF-81), 200 MB for the request. | Default, pending confirmation |
| DF-86 | **Signing limit.** One signing action carries 1 to 50 requests. | Default, pending confirmation |
| DF-87 | **Idempotency keys** are UUIDs. The server keeps the first result of a key for 24 hours; a key reused with a different body gives 422 VALIDATION_FAILED. For signing the key is the `signing_action_id` of the signatures; for the ERP send the request number is also the key sent to the ERP (DF-24). Releasing a batch and the resend need a short-lived key store that the architecture chooses. | Default, pending confirmation |
| DF-88 | **Rate limits.** Login: 10 attempts a minute for one email or one address. Every other operation: 600 requests a minute for one session. The answer is 429 `RATE_LIMITED` with `Retry-After`. | Default, pending confirmation |

## Gaps found in approved documents

These were found while reading the research, requirements, information architecture, UI/UX, and database documents. Approved documents were edited only where a placeholder belongs to the API (the matrix API column, the Related API lines, and the screen-to-API mapping). Each gap names the document and what would close it.

1. **No screen for the sync, and none for the simulated feeds.** No screen has a "Sync now" control (D-154), and no simulator screen edits the simulated authority status feed (`sim_authority_statuses`) or the tax-risk feed. AC-10.12 to AC-10.15 and AC-07.9 rely on seeded entries (D-120, DF-82), so the contract has no operation that writes `sim_authority_statuses`. If the demo should create such an entry by hand, the UI/UX needs a screen and API an operation.
2. **Message templates.** DF-21 says the Chief Accountant approves the three request templates, kept in configuration. No story, criterion, or screen lets the Chief Accountant approve one, so `listMessageTemplates` only reads them.
3. **Gate alert clearing.** `gate_alerts.cleared_by` and `cleared_at` have no rule in any source. D-152 closes it by a call.
4. **No table for sessions or idempotency keys.** D-131 and D-137 need both. Signing uses `signing_action_id` and the ERP send uses `erp_send_attempts.idempotency_key`, but a batch release has no column for a key. DF-87 leaves a short-lived store to the architecture.
5. **Invoice state history has no table.** `getInvoiceHistory` reads `audit_log` (AC-17.11, data model). This works only if every state change writes an entry that holds the previous state, the new state, and the BR-33 transition number in `details`. That is a requirement on the code of the implementation.
6. **Dashboard lists for the Entity Admin.** SCR-60 and AC-17.9 disagree (difference 9). D-155 is a reading; the user may prefer to give the Entity Admin a read-only list.
7. **`notification_kind` has no value for a rejected service acceptance** (difference 10).
8. **Unverified standards.** RFC 7807 (D-139) and the behaviour of the cookie flags (D-131) were not opened in this document set. A reading of RFC 7807 or RFC 9457, and of the cookie specification RFC 6265bis, would confirm them.
