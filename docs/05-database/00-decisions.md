# Decisions and Defaults

> Design status: MVP — Step 5 of 9, draft for review
>
> Implementation status: NOT STARTED

Numbering continues from Step 4 (decisions end at D-46, defaults end at DF-52). The Step 5 decisions are D-47..D-66 and the defaults are DF-53..DF-60. **Every row below is a call made while designing the schema. None is a decision of the user, and every row awaits user review.** The user's own scope decision D-33 (no foreign invoices, no PDF intake, no foreign tax duties, no payment method, no cash flag) is applied and not reopened: the schema has no table or column for them (see [Not modelled](01-data-model.md#not-modelled-in-step-5)).

Steps 1 and 2 are still draft for review and Steps 3 and 4 are approved. Where a schema need meets a gap or a wording in an approved step, the step is not edited. The difference is recorded in [Differences from Steps 1 to 4](#differences-from-steps-1-to-4) and the gaps are listed in [Gaps found in approved steps](#gaps-found-in-approved-steps).

## Decisions made in this step

| ID | Decision | Why | Status |
|---|---|---|---|
| D-47 | **PostgreSQL is assumed** for the schema and confirmed in Step 7 with the rest of the tech stack. [`matchpay.dbml`](matchpay.dbml) is the source of truth. The Mermaid diagrams in [02-er-diagram.md](02-er-diagram.md) are drawn from it, and the checker compares them with it. The file stays in this folder because the code layout is decided in Step 8. SQL migrations are written in Step 9. | The sample does the same. Partial indexes, exclusion constraints, and composite foreign keys need a SQL database with those features. | Awaiting user review |
| D-48 | **Entity isolation in the schema (BR-09, G-06).** Every business table has an `entity_id` that refers to `entities`. Only `corporate_groups`, `group_sectors`, and `entities` have none, and `users` and `audit_log` may have a NULL one (group-level users and events). The server takes the entity from the session and never from a request. A child row and its parent row must belong to the same entity: SQL uses composite foreign keys `(entity_id, parent_id)` on top of a unique `(entity_id, id)` on each parent, and the DBML keeps single-column references so that it stays readable. PostgreSQL row-level security on `entity_id` is recommended as a second layer and is decided in Step 7. | A single forgotten `WHERE entity_id = ...` would expose another entity's invoice. The constraint makes a cross-entity reference impossible to store, and the policy makes a missing filter return nothing. | Awaiting user review |
| D-49 | **The ERP simulator keeps the ERP side of the demo in `sim_*` tables** (personas, orders, order lines, receipts, receipt lines), and the sync copies them into the `erp_*` tables like any ERP. The master data of the simulator (suppliers, items, unit conversions, ERP users, the tax-risk feed) is seed files with no table, because US-08 only creates orders and receipts. `sim_*` tables have no foreign key to `erp_*`; the sync joins by reference. | MatchPay must never write to the ERP copy (BR-25), and US-08 needs somewhere to store the order and the receipt it creates (AC-08.1, AC-08.2). Step 6 must give every simulator operation an entity. Step 7 may place the `sim_*` tables in a separate schema or service. | Awaiting user review |
| D-50 | **The tax-risk list is stored per entity** (`tax_risk_entries.entity_id`), loaded in each entity's sync. | D-28 loads it through UC-07, which is a per-entity sync, and BR-09 says every record carries an entity code. A shared group table would be the only business table read by every entity. The cost is one copy of the same external list per entity. | Awaiting user review |
| D-51 | **The exact-duplicate check across the group is one partial unique index** on `invoices (seller_tax_code, series, number) WHERE holds_key`, and there is no separate key table. `holds_key` becomes true when the invoice passes the signature check and enters `In Check`. An invoice rejected earlier, and a rejected duplicate, do not hold the key. The insert that sets `holds_key` fails on a duplicate, and the server turns the failure into "An invoice with this seller, series, and number already exists". Nothing in the application reads other entities' rows to answer it (D-09, BR-09). | Two simultaneous uploads of the same key are stopped by the database and not by a race in code. The index is the only cross-entity structure in the schema. | Awaiting user review |
| D-52 | **The mapping table is keyed by entity, supplier, and normalized text** (`item_mappings`), not by text alone. | The same text from two suppliers can mean two items. BR-28 and AC-18.2 say "later lines with the same text match"; the schema reads this as the same text from the same supplier. It is a difference from the wording (see below). | Awaiting user review |
| D-53 | **One exception row belongs to one invoice.** The invoices of a split-order set (BR-10) have one exception each, linked by `split_finding_id`, and each carries `approval_amount` = the combined amount that decides the level. | Each invoice has its own state (BR-33), its own payment request line, and its own approval (AC-23.3 names "any of the three"). BR-10 says the invoices "become one exception"; the schema keeps the one decision and the one shared finding but not one row. | Awaiting user review |
| D-54 | **An individual approval is a row (`individual_approvals`) and the invoice becomes `In Batch` with `batch_items.admitted_via = INDIVIDUAL_APPROVAL`. The payment request is created when the batch is released**, as for every other request, and carries `individual_approval_id`. | AC-23.2 says the exception "becomes a single-invoice payment request in the open batch", but BR-35 gives a request no state before release (R1 creates it `Awaiting Chief Accountant`). The schema keeps the approval from the moment it is given and creates the request at B3. | Awaiting user review |
| D-55 | **The audit log is append-only and fails closed.** The application role has INSERT and SELECT on `audit_log` and nothing else, and a trigger refuses UPDATE and DELETE and TRUNCATE. The entry is written in the same transaction as the action it records (DF-30). `entity_id` is NULL for events outside any entity, and `is_group_event` marks the events the Group Admin may see. Its subject columns (`subject_type`, `subject_id`) are not foreign keys because the subject can be any table. | BR-12 says the log cannot be edited or deleted through the application. A database rule is stronger than an API that merely has no such route. A tamper-evident hash chain is not added because no rule asks for one. | Awaiting user review |
| D-56 | **Configuration objects carry a version too**: `corporate_groups`, `entities` (and `entities.matrix_version` for the approval matrix), `users`, `entity_policies`, `supplier_gates`, `recurring_profiles`. | D-30 and DF-27 name invoices, exceptions, batches, and requests. The Step 4 wireframes show the conflict state on SCR-70, SCR-73, SCR-74, SCR-76, and SCR-78, so those screens need the check as well. | Awaiting user review |
| D-57 | **Reading the XML is not an AI output.** The fields are columns of `invoices` and `invoice_lines`, read by a parser, and the original is stored unchanged in `invoice_documents.xml_content` (`bytea`) with its SHA-256. Rejected invoices keep their original as evidence. Whether the bytes stay in PostgreSQL or move to file storage is decided in Step 7; the hash stays in the database either way. | Task 2 of the AI list says "reads XML", but a parser is deterministic and has no model or prompt version to store (BR-12). Storing the bytes in the database keeps the hash and the content in one transaction. | Awaiting user review |
| D-58 | **Every check of an invoice is a run (`invoice_check_runs`).** The AI outputs and the Rule Engine decision of that run refer to it, and a re-check adds a new run and keeps the earlier ones (AC-16.13). | One place to measure G-05 (received to decision within 60 seconds), to show "Checking..." (Step 3 AI states), and to record an AI failure (`AI_FAILED`) without a half-written set of outputs. | Awaiting user review |
| D-59 | **Every embedding or LLM call is a row in `ai_requests`** with its task, model, prompt version, outcome, latency, and token counts. It holds no document text, no prompt, and no answer. | G-05 and R-10 need time and cost. A log with document text would copy invoice content into a second place (R-11, BR-27). | Awaiting user review |
| D-60 | **The send to the ERP is an outbox (`erp_send_attempts`).** The request becoming `Signed`, its invoices becoming `Signed`, and the first attempt row are saved in one transaction; a worker sends after commit, up to 3 attempts 5 minutes apart (DF-24). The ERP's answer (paid with a payment reference, or failure) is stored on the attempt and copied to the request. **BR-35 has no request state for an ERP failure after `Sent` (V19, AC-26.6).** The schema keeps the request `Sent` and sets `erp_failed_at` and `erp_failure_reason`; the invoices become exceptions "Payment failed". | An outbox is the only way to make "never a second payment" hold when the process stops between the commit and the send. The failure column is a stopgap: the state model needs a decision (see the gaps). | Awaiting user review |
| D-61 | **A signature is a row that is voided, never deleted.** `request_signatures` holds the signer, role, time, request version, content hash, simulated certificate, re-authentication time, and a `signing_action_id` shared by the signatures of one multi-sign action. Partial unique indexes allow one `VALID` row per request and signer and one per request and role. The content hash is SHA-256 of the canonical content of the request: its number, supplier, and each active line with its invoice hash and amount. | BR-20 and O-15 ask for one record per request with version and hash; BR-37 and R5 void earlier signatures when a line is removed. A signer can sign again after a void, so uniqueness must ignore voided rows. | Awaiting user review |
| D-62 | **Approval tiers are updated in place and never deleted** (`is_active`), and a request or an individual approval stores a copy of the level name it was judged at (`required_level_name`). | BR-03 recomputes the level of an unsigned request when the matrix changes, and a signed request keeps its level (AC-05.4). Without the copy, a later matrix change would rewrite history. | Awaiting user review |
| D-63 | **Derived values are computed when read and not stored.** The columns that are stored although derivable are listed with their reasons in the [data model](01-data-model.md#stored-although-derivable). | The sample does the same. A stored rate or badge can disagree with the rows behind it, and AC-27.6 requires that a figure and its list have the same count. | Awaiting user review |
| D-64 | **Two accumulated tables are added that the brief names under "accumulated data"**: `price_history` (BR-29) and `supplier_entity_stats` (BR-30). They are written when an invoice becomes `Paid` and are seeded in the demo (DF-42). | The demo seed has no paid invoices (DF-42 seeds history, not invoices), so "at least 3 purchases in 6 months" and "no previously paid invoice" cannot be read from invoices alone. Both tables stay per entity (BR-09). | Awaiting user review |
| D-65 | **Nothing is deleted in the MVP.** Users are deactivated, tiers, profiles, sectors, mappings, and risk-list entries are made inactive or get a removal time, and invoices, exceptions, batches, and requests end in a final state. The only rows that change after they are written are the ones with a state or a version. | BR-12 and AC-02.5 (earlier decisions and signatures stay). It also keeps every foreign key valid without cascade rules. | Awaiting user review |
| D-66 | **The current flow of an invoice is stored on the invoice** (`flow`, with `flow_set_by` when a person chose it), and the current item of a line is the latest `invoice_line_matches` row. The AI's own flow stays in `ai_flow_classifications`. | The worklist filters by flow (SCR-10), and a person's correction must not overwrite the AI's proposal that the gate accuracy compares with (DF-17). | Awaiting user review |

## Gaps found in approved steps

These are not edited. They need a decision before Step 6 or Step 9.

1. **No request state for an ERP failure after `Sent`** (BR-35, V19, AC-26.6). The request has no way to leave `Sent` when the ERP answers with a failure, the batch can then never reach `Completed` (B6 needs every request `Paid`), and AC-26.6 says "a new payment request needs new signatures" without saying which request is replaced. Options: a state `Failed` for requests, or a transition `Sent` to `Cancelled`. The schema has the two columns `erp_failed_at` and `erp_failure_reason` for either option.
2. **"Correct the entity" on SCR-12** (Step 3 inventory, Step 4 `correct` state) offers the three entities of the group, but an AP Accountant sees only the own entity (BR-09) and no story moves an invoice from one entity to another. The schema keeps `entity_id` fixed. Step 2 should say whether a different choice means "reject and ask for a reissue" (BR-01) or a transfer by someone with access to both.
3. **The timing of the individual-approval request** (AC-23.2 against BR-35 R1) and the meaning of "one exception" for split orders (BR-10 against AC-23.3). Differences 1 and 2 above show what the schema does; Step 2 should confirm or reword.
4. **BR-30 does not define "the period"** of a changed bank account (difference 9, DF-60).
5. **The seller's sector** (DF-58) and **where the AI's price history comes from** (DF-20 says "purchases of the item by the entity" without saying whether they are orders or paid invoices; D-64 chooses paid invoices plus the seed).
